# Automation adoption and replay vectors

This executable design slice models the point where Coven has already adopted an automation attempt and asks Psyche to adopt one orchestration request. Run `python3 conformance/automation-adoption/verify.py -v` and `python3 conformance/automation-adoption/verify_replay.py -v` from a clean checkout. `./scripts/agent-check full` runs both. The runners use Python 3.9+ and SQLite from the standard library. All IDs and authority evidence in the fixture are synthetic.

## Test interpretation

`verified-input.json` stands in for an independently verified producer projection. A real adapter needs the trusted producer, current fence, exact principal and project, verified familiar and Threads records, approval evidence, scoped runtime admission and a final validity/revocation check bound to adoption. The vector explicitly compares those fixture fields before the transaction and denies authority widening. It cannot establish actual authentication, containment or revocation ordering.

The runner reads the delivered bytes as strict UTF-8 JSON. It refuses a byte-order mark, another encoding, a repeated member at any depth, `NaN` and the infinities. The request, the trusted projection, the adoption result and every event have a closed shape with exact types: an unknown or missing member, a boolean or `3.0` where an integer belongs, and a counter outside 1 to 2^53-1 are refused. Timestamps are RFC 3339 in UTC with whole seconds and a literal `Z`. Each refusal is a `Denied`, `KeyConflict` or `ReplayError` with a stable reason code, and the tests assert the code of every refusal they provoke. A refusal happens before any write and is returned to the caller. The runners do not persist refusals. The codes are fixture vocabulary. Psyche's canonical structured-denial vocabulary belongs to `psyche-core` and is not defined here.

`request.json` is delivered as exact UTF-8 bytes, including the final newline. The candidate computes SHA-256 over those bytes for retained invocation identity. A second SHA-256 covers the UTF-8 brief. Neither digest changes the upstream producer's RFC 8785 digest rules. `result.json` is the adoption response. A successful adoption supplies stable correlation for lookup and subsequent events. It conveys no worker or automation terminal outcome.

Run `python3 conformance/automation-adoption/verify_replay.py -v` for process-exit and replay cases. The caller and Psyche keep separate SQLite files. A restarted caller uses its durable lookup key to recover a committed response. It keeps the request pending unless the result has the known adoption profile, the `adopted` state and the caller's own producer, key, request digest, occurrence, run and attempt. A restarted Psyche fixture retains the last committed active-lane observation and rolls back a later uncommitted write. Every event body names its producer, invocation key and execution. A restarted subscriber replays an unacknowledged event and applies it once. It refuses a body that names another execution, an adoption event that differs from the adoption it retained, a second adoption event, an unknown kind or lane state, a lane that moves from `returned` back to `active`, changed retained bytes, a gap and a page of more than eight events. A refused page leaves the cursor unchanged. All twenty golden cases have an explicit input, required observation, present evidence and remaining owner. [Golden scenario matrix](SCENARIOS.md)

The other proposed operations are `status` for authorized snapshots, `subscribe` for duplicate-safe bounded replay with an explicit cursor reset, `request_cancel` for adoption of a cancellation request, and `reconcile` for a retained response after uncertainty. A cancellation acknowledgement cannot settle either producer's terminal history. An ambiguous external effect requires recovery and stays ineligible for automatic retry. Approval and event lifecycle vectors require the owning protocols before these operations can be qualified.

## What these runners do not cover

- **Unbound request members.** `returnTo`, `cancelChannel`, `causeRef`, `cursor` and `retention` are checked for type, and `retention` for its one known value. The trusted projection does not carry them, so a first delivery with a different `returnTo` is adopted. The projection needs those members or a digest of the whole request before this becomes a contract.
- **Redelivery after expiry or revocation.** Exact redelivery of an adopted request is denied with `grant-expired` or `grant-revoked` once the grant has lapsed, while `lookup` of the same key still returns the adopted result. Which of the two a retried delivery should receive is an open contract question for #18.
- **Execution identifier.** `executionId` is `fixture-execution-` plus a SQLite row number. It is a fixture artefact: two stores issue the same value, and it is not the canonical Psyche ID construction. `result.json` and the byte-stable event vectors pin the value, so it was kept.
- **Fence currency.** The runner keeps no fence high-water mark. The fence vector proves that a generation differing from the trusted projection is denied. It does not prove staleness. Coven owns the fence.
- **Feed history.** Gaps on the producing side, compaction, snapshots and cursor reset are not modelled. A cursor beyond the retained stream is refused.
- **Lane transitions.** Only the order `active` then `returned` is checked for a lane. A changed lease, task or worker attempt on the same lane is not modelled.
- **Authority member names.** `verify_packages.py` compares the `source` members with the pinned Coven schemas. No runner compares the `authority` members with the Coven, Familiar Contract or Threads schemas.
- **Refusal records.** A refusal is not written to either journal.
- **Producer artifacts.** The two Coven artifacts expire on 2027-02-18. `source-pins.json` records the producer run and artifact IDs. No gate runs `verify_packages.py`, because it needs those downloads.
- **Platforms.** The runners were executed on macOS arm64 with Python 3.9.6 and 3.15.1. Linux and Windows were not run locally. The contributor workflow runs `./scripts/agent-check full`, and so both runners, on Linux, macOS and Windows.

## Run against the packaged Coven profiles

Download the two artifact ZIPs from the pinned Coven CI run and unpack each into its own directory. Give the inner tarballs to `python3 conformance/automation-adoption/verify_packages.py BASE_TARBALL AUTHORITY_TARBALL`. The runner checks the immutable tarball digests from `source-pins.json`, reads only the named archive members, and checks producer revisions and receipt placement. It verifies the packaged example’s binding/receipt correlation and rejects five changed sidecars. It then compares the `source` members of `request.json` and `verified-input.json` with the closed `base` object of the execution-binding schema and with `dispatchFence.dispatchGeneration` of the attempt schema: the member names, the identifier patterns and lengths, the counter minimums and the digest shape. It rejects six changed sources, including the earlier `attemptAdoptionKey` spelling and a source without `attemptNumber`. It reads no other fixture member. [Base artifact](https://github.com/OpenCoven/coven/actions/runs/44711462505/artifacts/14617741651) · [Runtime Authority artifact](https://github.com/OpenCoven/coven/actions/runs/44711462505/artifacts/14617701283)

Coven carries the immutable per-attempt binding under `AutomationRun.extensions["coven.automations.authority.v1"].executionBinding`. Its `base` holds definition, occurrence, run and attempt anchors. The authority profile adds the principal, familiar, Threads decision, approvals, exact capability grants, runtime and integrity. At settlement, the run’s `receiptEvidence` sidecar binds the base receipt digest to this binding. The base receipt schema is closed. The minimized sidecar carries the familiar root, revision and declaration digest, while its binding digest ties it to the execution binding that contains the embodiment digest. Reading the sidecar does not establish a current grant. Production consumers still need trusted live state, verified signatures and transactional decision consumption from the authority owner.

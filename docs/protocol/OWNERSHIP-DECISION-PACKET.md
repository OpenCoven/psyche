## ADR 1. Historical identity rebind

**Decide:** retain, replace or supersede `coven.familiar.identityRebind.v1`, and name the evidence for an unresolved adoption and for a prior session still able to act. The owner decides on #12. [Request](https://github.com/OpenCoven/psyche/issues/12#issuecomment-6303087073) · [Restated 20 November](https://github.com/OpenCoven/psyche/issues/12#issuecomment-7036420617)

| Option | Evidence and consequence |
|---|---|
| Retain the historical capability | Select its canonical owner and supported version. Keep affected routes closed until pinned real-daemon tests exercise old identity, unknown adoption, complete fencing and blocked routing. |
| Replace through an explicit old-to-current mapping | Name the producer, contract and version, canary and denial for each historical guarantee, including survivors, unresolved adoption and restart. Only specifically proven rows can migrate. |
| Supersede or retire it | Record why each old guarantee is preserved elsewhere or why the route is removed, which consumers lose compatibility, and how rollback preserves identity. Unmapped guarantees remain open. |

**Evidence.** The Telegram record already retains the rebind obligations and splits them: Familiar Contract stays the identity authority, Psyche owns the audited migration orchestration, Threads constrains protected changes, and Coven proves old execution terminality or fencing. The same record leaves the historical control action as an unresolved compatibility obligation, requires an old-to-current mapping with executable equivalence evidence on Coven #1230, and says not to add familiar or person authority to Coven to reproduce the historical name. The Coven matrix found no match for the action in current crates or the API contract, and no direct equivalent in the C-S rows. The O4 approval does not decide the mapping. [Telegram record, items 3 and 4](https://github.com/OpenCoven/psyche/issues/12#issuecomment-6303089462) · [Coven matrix](https://github.com/OpenCoven/coven/issues/1230#issuecomment-6303076065) · [O4 scope](https://github.com/OpenCoven/psyche/issues/12#issuecomment-6518635677)

**Recommendation: replace through an explicit mapping.** Retaining the action as named needs a single owner for a Coven control action that carries familiar authority, which the Telegram record warns against. Superseding it needs a reason to remove guarantees that the record explicitly retains. A mapping keeps every guarantee visible and lets each row close on its own evidence. A route change must identify the prior session, old and candidate principal and snapshot, project, attempt, immutable request, authority and disposition. The producer must prove resolution or complete fencing before any route acts under the replacement identity. Uncertainty keeps the route blocked.

## ADR 3. Process-attempt fence issuer and coverage

**Decide:** the trusted issuer of a `Fenced` disposition for a process-bound attempt, the enforcer that can prove the old process, delegated descendants and dispatched tools can no longer act, and how that proof replays after a host restart. The owner decides on #12. Issue #19 also asks for producer and consumer approval of the resulting profile. [Psyche #19](https://github.com/OpenCoven/psyche/issues/19) · [Request](https://github.com/OpenCoven/psyche/issues/12#issuecomment-7036795474)

| Option | Evidence and consequence |
|---|---|
| The graph-owning host issues (PR #20) | The host supplies the immutable correlation and issues `Fenced` only after every old actor has lost the ability to act. The consumer stores the binding, replays against the host and blocks dispatch when the host is unavailable or returns `Unresolved`. |
| A different producer and evidence chain | The owner names the issuer, its authentication, and the evidence for each surviving resource. The fixtures in PR #20 would need rebinding to that issuer. |

**Evidence.** `ReconciliationDisposition::Fenced` already carries a disposition ID, an opaque fence token, the exact `ExecutionCorrelation`, the ambiguity digest and the recorded time, so the open question is authority and not token shape. Coven's invocation record does not own Psyche graph, node or familiar identities, and #19 forbids minting them in `coven-agents`. Process death, dropped futures, empty live-attempt registries and O4 admission exclusion do not prove containment. PR #20 at `5ec5b67cec1975a77879a452b02e226aaf00c244` adds the proposed profile and fixtures and lists issuer authentication, all-actor loss of effect and replay across a real host restart as remaining qualification. [Fenced disposition](../../crates/psyche-coven/src/port.rs) · [Consumer coordination](https://github.com/OpenCoven/psyche/issues/19#issuecomment-6621892147) · [PR #20](https://github.com/OpenCoven/psyche/pull/20) · [Journal results](https://github.com/OpenCoven/psyche/issues/19#issuecomment-7037091923)

Two recorded facts need reconciling in the decision. The Telegram record assigns sessions, execution admission, adoption and fencing, and terminal state to Coven. On main `CovenPort::reconcile` returns the disposition from the Coven side to Psyche. PR #20 proposes the opposite direction for an in-process invocation, with the host issuing to the consumer. The threads do not say whether these are one fence or two.

**Recommendation.** Approve the graph-owning host as issuer of the disposition for the #19 profile only, because it is the only party that holds the correlation the disposition must match. Require authenticated containment evidence from the owner of each resource that can still act, with Coven as that owner for its sessions under the Telegram record. The enforcer for an in-process attempt is not established, so return that part to #19 and Coven #804 with the fixture list from #19. Until the evidence exists, an abandoned, termination-unknown or recovery-required attempt stays non-dispatchable. A fenced disposition resolves ambiguity for that attempt only. A fresh dispatch needs its own admission.

## ADR 4. Build receipt binding

**Decide:** the released record or projection that binds Build's task ID, action or idempotency key and exact terminal receipt to Psyche's execution request ID and digest, its issuer, its verifier, and what the verifier reports when durable evidence is missing, ambiguous or conflicting after restart. The owner decides on #12. This is the first Build adoption gate. [Question](https://github.com/OpenCoven/psyche/issues/12#issuecomment-7074231074) · [Restated after the corrected canary](https://github.com/OpenCoven/psyche/issues/12#issuecomment-7076215099) · [Adoption gate](https://github.com/OpenCoven/psyche/issues/13#issuecomment-7075947867)

The threads ask the question without listing options. The three below are the shapes the cited evidence admits.

| Option | Evidence and consequence |
|---|---|
| A. Psyche issues a released binding record | #11 defines a record in the Psyche registry that carries the request ID and digest, the receipt digest and Build's identifiers as opaque references. G2 records deny unknown fields, so this needs a new wire shape or negotiated revision and a fresh G2 attestation. It also needs a Psyche-side issuer in the Build flow, which no thread describes yet. |
| B. Release the experimental projection as it stands | Build keeps the binding in its native journal and a released Psyche checker compares request ID, digest and receipt bytes. This is the cheapest path. Build's journal would then be the only durable source of the binding, and the kit review shows the current checker trusts what the adapter reports. |
| C. Keep the binding experimental | The canary stays reviewable and Build adoption stays unqualified. |

**Evidence.** The registry has 16 kinds and 15 record identities and no separate prefix for task, lane, action, receipt or lease. The experimental kit keeps Build's task, action, approval and receipt references in Build, compares opaque receipt bytes and grants no execution authority. On Ubuntu and macOS it held the same task ID, action, approval ID and digest, receipt hash and effect count across first delivery, restart and native rollback, and a lost acknowledgment stayed unknown with one witnessed execution. Those runs qualify the exact Build fixture. An independent review of the generic kit then showed that it takes the effect count from the adapter's own reply, so an adapter that re-executes and under-reports still passes, and that its lost-acknowledgment vector prescribes plain resubmission with no fence or reconciliation token. Six findings are open and the kit integration is on hold. Build's merged map classifies action identity and receipt as Psyche-owned target semantics after profile release, lets the adapter build a receipt projection only from the authoritative terminal path, and on restart surfaces unknown or quarantine and never reruns an effect. Build PR #599 merged at `e7ae2b4258de3ba3efff57fe84d5acce263ead33`. Producer PRs #39, #41, #43 and #44 and Build PR #600 are open. [Schemas](../SCHEMAS.md) · [Missing representations](https://github.com/OpenCoven/psyche/issues/13#issuecomment-7036796121) · [Canary results](https://github.com/OpenCoven/psyche/issues/13#issuecomment-7076251240) · [Kit review](https://github.com/OpenCoven/psyche/pull/41#issuecomment-7076475139) · [Build map](https://github.com/OpenCoven/psyche-build/blob/73dc6f5d733745894385f906c2f0993f1fd1f818/docs/PSYCHE-COMPATIBILITY-MAP.md) · [Receipt profile PR #39](https://github.com/OpenCoven/psyche/pull/39) · [Lifecycle kit PR #41](https://github.com/OpenCoven/psyche/pull/41) · [Build PR #599](https://github.com/OpenCoven/psyche-build/pull/599) · [Agent guide](../../AGENTS.md)

**Recommendation: option A, with the option B comparator kept as the consumer check.** The proposed baseline and Build's own map both place the receipt lifecycle with Psyche, and option B alone would leave Build as a hidden source of canonical truth for the binding, which the cross-repository rule in the agent guide forbids. The physical terminal fact still comes from the authoritative effect path and never from UI or process state. Build's identifiers enter as opaque references that cannot replace a Psyche ID, prove authority or prove completion. The verifier is the pinned Psyche runner recomputing the request and receipt digests. It should not accept an effect count that the consumer reports about itself, which is the gap the kit review found. For the disposition: a missing outcome reports unknown and recovery-required, an ambiguous outcome stays unknown until canonical reconciliation, and a conflicting outcome preserves the original record and quarantines the other. None of the three reports success or permits another effect. The record's name and fields belong to #11 and are not proposed here.

## Compatibility, release order and rollback proposal

```text
Familiar Contract    Coven Threads    Coven Runtimes    Coven daemon contracts
       |                   |                |                   |
       +-------------------+----------------+-------------------+
                                      |
                                Psyche profile
                                      |
                    +-----------+-----+-------+-----------+
                    |           |             |           |
                Psyche Build   Cave          SDK        Memory
                                      |
                         consumer evidence to #13
```

Arrows indicate which published input a consumer pins. Docs can read each producer's artifacts. Consumer reports return to the tracker as evidence. No producer contract depends on a Build or Cave release to define its meaning. Runtime integration may call both directions using published interfaces without introducing a release dependency cycle. During promotion, record the exact version and digest of each dependency and walk the graph from source to each consumer. Any edge back to a consumer that defines its producer's semantics blocks promotion.

1. Each producer publishes immutable versioned facts and bounded acceptance/rejection vectors. The Psyche owner reviews the rows and selects one exact supported profile. Unrecognized schema major, enum, required capability or authority scope fails closed. G2 strict fields mean even an added field needs a negotiated revision or a new wire shape. Never infer compatibility solely from a minor-version number.
2. #11 packages the selected rows and their compatibility range. Changing authority, identity, persisted meaning, required fields or narrowing a previously accepted reader's input requires explicit migration and rollback proof. Add optional capabilities only where existing readers can omit them and unchanged behavior is demonstrated. Start the support window with one qualified exact profile. Widen it only after testing each producer/consumer pair.
3. Build pins manifest, artifact digest, signature identity, producer revision, runner version and vector digests. Run the existing and candidate pins on an isolated copy of representative persisted state. Require success for accepted operations and exact denials for stale scope, widening, unknown major, ambiguity, restart and incompatible downgrade. Cave, SDK and Memory run their bounded profile subsets before claiming support.
4. Roll out behind the consumer adapter switch, keep old correlation and durable read paths, and preserve transactional writes or an explicitly reversible migration. To roll back, disable new writes, restore the previously accepted pin, reopen previously migrated records, and verify the exact original IDs, authorities and receipt chain. An old reader that cannot prove compatibility must block the write and preserve the original bytes.
5. Deprecate with a named replacement, supported consumer list, migration horizon and observed old-pin usage. Remove only after dependent owners record migration or explicitly retire the profile. For emergency revocation, the producer identifies affected immutable digests and constrains or disables the operation. Resume only against a reviewed pin with fresh negative canaries and durable reconciliation of outstanding effects.

## Contract-change review and reference flow

A change request must name each changed fact and producer, affected clients, prior and proposed compatibility range, immutable source and artifact pins, expected positive and denial outcomes, migration/rollback fixtures, actual canary results, qualified platforms, deprecation horizon and reviewer. The release owner records the approved rows and any excluded obligations. Approval trails for #10, the #12 decision, the release in #11 and each consumer canary must remain separately identifiable.

For the Build reference scenario, create one task and isolated lane on a pinned client, capture its protocol IDs, start one correlated attempt and require an approval tied to one scoped action. Persist the authoritative receipt, disconnect, restart and reopen the original task. Compare project, task, lane, attempt, action, approval and receipt and verify zero repeated effects. Change the local pane, path, provider session or selected tab and confirm the same identity resolves. Repeat with a stale approval and an ambiguous delivery; retain the exact denial or unknown state. Disable the adapter, restore the supported old pin and verify the same task reopens without data loss or identity fork. Record exact pin, consumer SHA, macOS behavior, CI and evidence on #13 and Build #253/#201. [Merged Build map](https://github.com/OpenCoven/psyche-build/blob/73dc6f5d733745894385f906c2f0993f1fd1f818/docs/PSYCHE-COMPATIBILITY-MAP.md) · [Reference flow](https://github.com/OpenCoven/psyche/issues/13)

The experimental canary covers the restart, replay, denial and rollback steps of this scenario with Build's native identifiers and a synthetic effect. It qualifies the exact Build fixture, and the generic kit still has six open findings. It does not cover protocol-owned task, lane, action or receipt IDs, which wait on ADR 4.
